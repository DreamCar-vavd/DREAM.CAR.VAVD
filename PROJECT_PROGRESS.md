## Етап 3 (фінальна перевірка галереї) — 2026-08-06

### Корінна причина проблем із галереєю — знайдено і виправлено
Файлів `public/images/gallery/01.jpg`…`08.jpg` **не існувало на диску** (лише шлях був заданий у коді як плейсхолдер-заглушка) — звідси всі 404 в мережі. Крім того, Next.js закешував старі 400-помилки оптимізатора зображень (`.next/cache/images`) ще з моменту, коли файлів не було.

**Виправлення:**
1. Згенеровано 8 реальних JPG-плейсхолдерів у [public/images/gallery/](public/images/gallery/) — правильні розміри (800×1000 для непарних, 800×800 для парних, згідно з [content/gallery.ts](src/content/gallery.ts)), елегантний дизайн у стилі сайту (темний градієнт, тонка золота рамка, декоративне золоте кільце — перегукується з іконками послуг). Це справжні coректні placeholder-зображення, а не биті шляхи — легко замінити на реальні фото пізніше під тими самими іменами.
2. Очищено `.next/cache/images` — прибрано застарілі закешовані помилки.
3. [GalleryGrid.tsx](src/components/GalleryGrid.tsx): CSS-верстку галереї спрощено з `columns-*` (мультиколонковий masonry) на звичайний `grid` — надійніший, менш вибагливий до рендер-двигуна підхід (сама галерея, як і раніше, адаптивна: 2/3/4 колонки).

### Перевірка (3 незалежні методи)
1. **curl напряму до сервера** — усі 8 запитів `/_next/image?...gallery/0N.jpg...` (різні ширини: 640/828/3840px) → `200 OK`, коректний `Content-Type: image/jpeg`.
2. **DOM/JS у самому Preview (`naturalWidth`/`complete`)** — після очищення кешу й перевантаження всі 8 `<img>` в галереї: `complete: true`, `naturalWidth: 320`, правильні пропорції (320×400 і 320×320).
3. **Playwright (незалежний Chromium)** — навігація на `/uk#gallery`: **Console: 0 errors**, усі 8 зображень `complete: true`, `naturalWidth: 253` (пропорційно коректні). Скриншот галереї — чисто відображається, без биті іконок.

**Отже, пункти 1, 2 і 4 із запиту повністю виконані**: усі 8 зображень завантажуються без помилок, коректний `naturalWidth > 0`, правильні шляхи; у Console/Network — 0 помилок зображень, 0 JS-помилок.

### Пункт 3 — чорний екран Preview: НЕ вдалося повністю усунути (чесно, без прикрас)
Під час скролу саме до секції "Галерея" вбудована панель Browser Preview (окремо від Playwright) стабільно показує чорний екран — відтворено повторно навіть **після**:
- очищення кешу зображень і виправлення 404,
- заміни CSS `columns` на `grid` (щоб виключити верстку як причину),
- повного перезавантаження сторінки й повторного відкриття нової вкладки Preview.

Паралельно перевірено: `vm_stat` під час кожного відтворення показував критично мало вільної пам'яті (~60-65MB). У Playwright (окремий движок) та через прямі curl/DOM-перевірки та сама секція завжди рендериться коректно й миттєво. Це вказує на те, що причина — обмеження ресурсів конкретно панелі Browser Preview на цій машині зараз (ймовірно, брак пам'яті для GPU-композитора при одночасному декодуванні 8 зображень), а не дефект коду сайту. Технічно довести це на 100% неможливо без доступу до внутрішньої діагностики самої панелі перегляду.

**Доказовий скриншот галереї** (через Playwright, де рендер стабільний): `progress-screenshots/08-gallery-verified.png`.

## Розслідування причини аномальних затримок 60–300+с + кешування — 2026-08-13

### Підтверджена (часткова) причина
`getDictionary()` — викликається **6 файлами** (`layout.tsx`, `page.tsx`, `privacy-policy/page.tsx`, `services/[slug]/page.tsx`, `cookies/page.tsx`, `cars-for-sale/page.tsx`) — на кожен виклик робить `await readGalleryProjectOverrides()`, яка читає `src/content/gallery-project-overrides.json` (1277 байт) з диска **без жодного кешування**. Для ОДНОГО HTTP-запиту `getDictionary()` викликається мінімум **двічі** (`layout.tsx` для Header/Footer + сам `page.tsx`) — тобто 2 зайвих дискових читання на кожен запит без винятку.

**Профілювання (ізольований `fs.readFile`, 5 семплів):** перше читання — 585.7мс (холодне), наступні — 0.4мс/0.14мс/0.1мс/0.1мс (тепле, з кешу ОС). **Чесний висновок:** саме дискове читання, навіть під поточним навантаженням, не перевищує ~600мс ізольовано — це НЕ пояснює багатохвилинні затримки самостійно. Знайдено докази, що навіть повністю прогріті маршрути (`/uk`, відвідуваний сотні разів) одноразово показували `application-code: 5.6min`, `/uk/services/detailing` — 4.1хв, `/uk/services/srs-airbag` — 2.9хв — це вказує на ширше системне навантаження (CPU/swap/диск), що затримує обробку Node.js event loop, а не конкретно цей файл.

### Обраний механізм кешування

Обрано замість `unstable_cache`/persistent-кешу свідомо: scope — **лише один HTTP-запит**, без будь-якого збереження між запитами → жодного ризику застарілих даних, витоку між користувачами чи "вічного" кешування помилки. Файл overrides **може змінюватись** під час dev-сесії (через `writeGalleryProjectOverride`, викликану з dev-only `/api/gallery-projects/[id]` — підтверджено читанням коду) — `React.cache()` коректно обробляє це: кожен НОВИЙ запит завжди читає диск заново.

## Термінова точкова правка: усунення розмитої "плями" на стіні позаду Hero-логотипа — 2026-08-13

### Вимога користувача
Попередній фікс (заміна старого знака, див. розділ вище) залишив позаду нового логотипа помітно **розмиту прямокутну ділянку стіни** (наслідок методу "суцільна маска + 60 ітерацій Gaussian Blur"). Нова вимога: прибрати саме це розмиття, зберігши новий логотип **абсолютно незмінним** (позиція, розмір, кольори, пропорції), відновити чітку, зернисту, натуральну текстуру стіни навколо й позаду нього.

### Причина розмиття (аналіз)
Попередній метод використовував суцільну прямокутну маску `X:1275–1682, Y:0–290` і 60 ітерацій `GaussianBlur(14)` — це технічно "розмиття", а не "відновлення текстури": втрачено зернистість/шум камери на всій площі прямокутника, що на реальному фото виглядає як чужорідна м'яка пляма.

### Новий метод (без розмиття як результату)
1. **Точна маска за формою гліфів, не прямокутник.** Побудована через `numpy`/`scipy.ndimage`: комбінація (a) локального контрасту відносно сильно розмитої (σ=35, лише для АНАЛІЗУ, не для заповнення) оцінки фону стіни та (b) кольорової сигнатури золото/білий текст. Це дало точну маску форми корони, "DREAM.CAR.VAVD", "AUTOMOTIVE SERVICES" та декоративних ліній — **не прямокутник**. Маска додатково очищена (`binary_closing`) і розширена (`binary_dilation`, 6 px) для повного покриття анти-аліасингу/світіння країв гліфів.
2. **Виключення контамінованої зони.** Виявлено і виключено з донорських пікселів вузьку смугу `X:1300–1332` (тепловідблиск червоної стійки підйомника на стіні поруч), щоб вона не "протікала" у відновлену текстуру.
3. **Структурне заповнення:** `cv2.inpaint()` (алгоритм Telea, `inpaintRadius=10`) — заповнює лише замасковані пікселі гліфів, використовуючи реальні сусідні пікселі стіни; це не є "застосуванням блюру до зображення", а спрямоване структурне відновлення.
4. **Відновлення чіткої зернистості:** з реальних необроблених пікселів стіни в тій самій ROI обчислено high-frequency залишок (`оригінал − GaussianBlur(σ=3)` — блюр тут лише як математичний інструмент розділення частот для АНАЛІЗУ, не як фінальний результат), який методом clone stamp (nearest-neighbor, `scipy.ndimage.distance_transform_edt`) перенесено на замасковані пікселі — це повертає справжню фотографічну зернистість, а не гладку заливку.
5. М'яке розтушування (`GaussianBlur(σ=1.0)` на самій масці, 1px) — лише для плавного переходу на межі маски, без різкого шва.
6. Область редагування обмежена `Y:0–235` (безпечний відступ від полиці з інструментами й підсвіткою знизу, яка починається приблизно з Y≈252) і виключає червону стійку підйомника зліва.

**Чесно про залишкове незначне пом'якшення:** через невелику площу (~48000px, 4.8% зображення) метод дає високоякісний, різкий, зернистий результат при перегляді в реальному масштабі сайту; при штучному 2× збільшенні під новим логотипом ще ледь помітна дуже слабка тональна нерівномірність (типове обмеження content-aware fill на великих ділянках низькоконтрастної стіни) — але вона **майже повністю прихована під самим логотипом** у фінальній композиції і **непомітна** при перегляді на реальному розмірі Hero-блоку (підтверджено скріншотами нижче).

## Брендована 404-сторінка (UK/RU/EN) — 2026-08-14

### Вимога користувача
Локалізована UK/RU/EN сторінка 404 (чорний фон, золоті акценти, справжній логотип, кнопка повернення) відповідно до документації встановленого Next.js 16.3.0, зі справжнім HTTP-статусом 404.

### Пройдений шлях (чесно, включно з відхиленими підходами)
1. **`global-not-found.tsx` + `experimental.globalNotFound`** (Next.js 16.3.0) — реалізовано першим. Ловить URL, що **взагалі не збігаються з жодним маршрутом** (напр. `/uk/invalid-page-test`) — і показує брендовану сторінку коректно. **Не ловить** `/xx` (невалідне значення `[locale]`), бо там `notFound()` викликається зсередини вже узгодженого сегмента `[locale]/layout.tsx` — інший механізм за документацією.
2. **Спроба виправити `<html lang>`** через `export const dynamicParams = false` + `next/root-params`. **Провалилась**: `dynamicParams=false` не переспрямував `/xx` на `global-not-found`; `next/root-params`'s `locale()` кинув `TypeError` (HTTP 500) — геттер не існує, бо в цій структурі проєкту `[locale]/layout.tsx` НЕ є справжнім root layout (є окремий `app/layout.tsx`). Код повністю відкочено до робочого стану (підтверджено tsc/eslint/test).
3. **Read-only аудит** видалення `app/layout.tsx` і route group `(root)` — з'ясовано, що `src/app/page.tsx` (редирект з `/`) зламався б без окремого layout; сам по собі `(root)`-рефакторинг теж **не гарантує** вирішення проблеми `/xx` (недокументований edge-case). Нічого не реалізовано.
4. **Контрольований експеримент: `src/proxy.ts` з internal rewrite** — успішний. Proxy перехоплює запит **до** рендеру маршруту, перевіряє перший сегмент шляху; якщо це не `uk`/`ru`/`en` (і не службовий шлях), робить `NextResponse.rewrite()` на навмисно неіснуючий sentinel-шлях `/__proxy_404__/nf`. Це змушує Next трактувати запит як "URL не збігається з жодним маршрутом" — і `global-not-found.tsx` спрацьовує коректно, з реальним HTTP 404, без зміни URL у браузері.

### Прийняте рішення
**Варіант 4 (proxy.ts + internal rewrite) — прийнято користувачем як остаточне.**

### Створений файл
`src/proxy.ts` — єдиний новий файл. Повний вміст:
```ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";
import { locales } from "@/lib/i18n/config";

const SENTINEL_PATH = "/__proxy_404__/nf";

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;

  if (pathname === "/") return NextResponse.next();
  if (pathname.startsWith("/api")) return NextResponse.next();
  if (pathname.startsWith("/_next")) return NextResponse.next();
  if (pathname === "/favicon.ico") return NextResponse.next();
  if (pathname === "/robots.txt") return NextResponse.next();
  if (pathname === "/sitemap.xml") return NextResponse.next();
  if (pathname.startsWith("/__proxy_404__")) return NextResponse.next();

  const lastSegment = pathname.split("/").pop() ?? "";
  if (lastSegment.includes(".")) return NextResponse.next();

  const firstSegment = pathname.split("/")[1] ?? "";
  if ((locales as readonly string[]).includes(firstSegment)) {
    return NextResponse.next();
  }

  return NextResponse.rewrite(new URL(SENTINEL_PATH, request.url));
}

export const config = {
  matcher: [
    "/((?!api|_next/static|_next/image|favicon.ico|robots.txt|sitemap.xml).*)",
  ],
};
```
`src/app/global-not-found.tsx`, `src/components/NotFoundContent.tsx`, `next.config.ts` (`experimental.globalNotFound: true`) — залишились у стані, реалізованому раніше в цій самій сесії; **не змінювались** під час роботи над proxy.
