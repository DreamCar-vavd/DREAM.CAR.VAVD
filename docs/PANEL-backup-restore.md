# Резервування й відновлення контенту панелі

## Що де зберігається

| Дані | Місце | У Git? | Резервування |
|---|---|---|---|
| Опублікований знімок (`published.json`) | репозиторій | ✅ | історія Git + `npm run content:export` |
| Робочі копії (`src/content/cms/**`) | репозиторій | ✅ | те саме |
| Стан перевірки мов (`review-state.json`) | репозиторій | ✅ | те саме |
| Фото авто / галереї / послуг / банерів | `public/images/cms/**` | ✅ | те саме |
| **Завантажені відео** | Vercel Blob (hosted) / `public/uploads/videos/` (dev, git-ignored) | ❌ | окремо — копія bucket'а / теки |
| **Заявки** | Postgres (`LEADS_DATABASE_URL`) | ❌ | засоби провайдера (Neon PITR + `pg_dump`) |
| Дані Vercel Analytics | Vercel | ❌ | Web Analytics API / дашборд (не критично) |
| Секрети (env) | Vercel Environment Variables | ❌ | менеджер паролів власника |

> **`git clone` — це НЕ повний бекап.** Він не містить відео, БД заявок,
> аналітики й секретів. Повний бекап = `git clone` **плюс** копія відео-сховища
> **плюс** дамп БД заявок.

## Експорт контенту

```
npm run content:export
```

Пише `export/<timestamp>/` з `published.json`, `review-state.json`, усіма
робочими копіями, **лише** referenced медіа, `MANIFEST.txt` (sha256 кожного
файлу) і `EXTERNAL-RESOURCES.md` (що поза Git). Падає, якщо якесь посилання в
`published.json` не резолвиться у файл. Тека `export/` — у `.gitignore`.

Перевірено на синтетичному наборі: 70 файлів, 51 медіа, 0 «висячих» посилань,
кожне фото з `published.json` має відповідний файл на диску.

## Відновлення попереднього опублікованого матеріалу

`published.json` версіонований у Git, медіа **ніколи не видаляється**
автоматично (ні `content-guard`, ні панель — лише ручна дія в `/panel/video`
для відео). Тому відкат безпечний:

1. **Один матеріал** (напр. авто зникло / зіпсувалось у знімку):
   - у `/panel` натиснути **«Прибрати з сайту»** (unpublish) — робоча картка
     лишається, або
   - взяти попередню версію запису:
     `git show <старий-sha>:src/content/cms/published.json` → скопіювати
     потрібний елемент масиву назад і опублікувати через `/panel` (повторна
     публікація сама перезапише `review-state.json` для цього матеріалу).
2. **Весь знімок — `published.json` І `review-state.json` з того самого SHA:**
   ```bash
   git checkout <старий-sha> -- src/content/cms/published.json src/content/cms/review-state.json
   npm run content:guard        # має бути ✓
   git commit -m "restore content snapshot @ <sha>" && deploy
   ```
   **Чому обидва файли:** `content-guard` звіряє кожен мовний текст знімка з
   хешем у `review-state.json`. Якщо старий знімок містить матеріал, який
   згодом видалили, його review-хеші вже вичищені — відкат лише `published.json`
   тоді **валить guard** (`текст не позначено перевіреним`). Звірено локально
   (задача 16:08 блок 6): відкат лише `published.json` з `803361e` → guard ✗
   на `zzz-test-panel`; відкат обох файлів → guard ✓, усі 53 медіа на місці.
3. **Робоча картка:** `git checkout <sha> -- src/content/cms/<kind>/<id>.json`
   (не впливає на опублікований знімок — guard лишається ✓).

Медіа старого знімка гарантовано присутнє, бо guard за весь час нічого не
видаляв; якщо файл усе ж прибрали вручну — `git checkout <sha> -- public/images/cms/...`.

**Розмежування обʼєктів відкату:**

| Обʼєкт | Чим є | Спосіб відкату |
|---|---|---|
| Код + контент (`published.json`, робочі копії, `review-state.json`, медіа в `public/`) | версіоновано в Git | `git checkout <sha> -- <шлях>` — це **git-відкат коду**, а не бекап зовнішніх сховищ |
| Відео у Blob / БД заявок Postgres | **поза Git** | лише засобами провайдера (Blob-бекап, Neon PITR / `pg_dump`) — `git checkout` їх не відновлює |
| Секрети (env) | **поза Git** | лише з менеджера паролів власника (див. нижче) |

Матеріал, «опублікований, але без робочої копії» (відкат старого знімка, чию
робочу картку потім видалили), панель показує як orphan-рядок — це очікувано,
`/panel` це обробляє; за потреби відновити й робочу картку кроком 3.

## Відновлення відео

Посилання в `published.json` (`video.src`) дійсне, лише поки живий файл за URL.
Якщо відеофайл втрачено:
- **dev:** відновити `public/uploads/videos/<key>` із копії теки, або
  перезавантажити через `/panel/video` (з'явиться новий key — оновити
  `video.src` у Keystatic).
- **hosted:** відновити об'єкт у Blob-сховищі з його бекапу, або
  перезавантажити.

Видалення відео в чернетці **не ламає** опублікований знімок: знімок містить
власну копію `video.src`, а не посилання на робочу картку.

## Відновлення бази заявок

Схема — `src/lib/leads/schema.sql`. Провайдер:
- **Neon:** Console → Branches → Restore (point-in-time), або `pg_dump` за
  розкладом у власне сховище.
- Загальне: `pg_dump "$LEADS_DATABASE_URL" > leads-YYYY-MM-DD.sql`.

Персональні дані: дампи тримати зашифрованими, не в Git, видаляти за політикою
зберігання (нижче).

## Політика зберігання заявок (пропозиція — рішення власника)

- **Зберігання:** 24 місяці активних записів у БД, далі — `deleted_at`
  (м'яке видалення, поле вже є у схемі), ще через 6 місяців — фізичне
  видалення дампом-та-перезаливкою.
- **Експорт:** `pg_dump` раз на тиждень у приватне сховище власника.
- **Видалення на запит суб'єкта даних:** ручний `UPDATE leads SET deleted_at =
  now() WHERE …` + видалення з наступного тижневого дампу.
- **Автоматичного очищення код не робить** — лише за окремим погодженням.

## Захищена копія секретів (робить ВЛАСНИК; агент не створює)

Секрети — це **не** git-обʼєкт і **не** входять у жоден git-відкат. Копію
робить лише власник, у власне захищене сховище. Коротка інструкція:

1. Vercel → Project `dream.car.vavd` → Settings → Environment Variables.
2. Для кожної змінної (`CONTACT_FORM_ENDPOINT`, `KEYSTATIC_*`, майбутні
   `LEADS_DATABASE_URL`, `BLOB_READ_WRITE_TOKEN` тощо) записати **назву,
   середовище (Production/Preview), значення** у менеджер паролів власника
   (1Password / Bitwarden / Apple Keychain) — окремим записом «DREAM.CAR.VAVD
   — Vercel env».
3. Оновлювати цей запис при кожній зміні/ротації змінної.
4. Значення **ніколи** не потрапляють у Git, чат, звіти, скриншоти.
5. Відновлення: вручну повторно додати змінні у Vercel з цього запису →
   redeploy.

Агент може лише **нагадати** про цей крок і звірити список **назв** змінних —
не значень.
