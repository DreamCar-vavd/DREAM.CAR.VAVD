### Правила

- Пароль від зашифрованих образів **не зберігати поруч із зашифрованим файлом**.
- Секрети (значення змінних середовища, доступи) — **лише в менеджері паролів**.
- Recovery-коди — **окремо** від носіїв із комплектом.
- Флешку й зовнішній диск зберігати **від'єднаними**; підключати лише для запису
  або перевірки.
- Новий комплект — **після великих змін** (нові функції, публікації, зміни
  панелі) і **щонайменше раз на місяць**.
- **Не видаляти попередню копію**, доки новий комплект не пройшов перевірку
  відновлення.
- Персональні дані клієнтів (заявки) у комплект не включати; незашифрованих копій
  із ними не створювати.
- **Особисті оригінали фото й відео** (з телефона, камери, теки `-FOTO-CAR-`)
  резервувати **окремо**: комплект сайту гарантує збереження файлів репозиторію й
  CMS, але не всіх особистих оригіналів. Цей документ не підтверджує, що така
  окрема копія вже існує.

### Як створити новий комплект (коротко)

1. Звірити remote `main` і `panel/content` (`git ls-remote`, GitHub API).
2. У тимчасовій папці: `git clone --mirror` → `git bundle create … --all` →
   `git bundle verify`.
3. Зі свіжого клону `main`: `npm run content:export`; окремо скопіювати весь
   `public/` і документацію (без `.env`-файлів).
4. Метадані без секретів (GitHub API, DNS) → `external-resources/`.
5. Пробне відновлення з bundle у новій тимчасовій папці: refs, SHA, дерево,
   `git fsck`, `npm run content:check`, порівняння `public/`.
6. `RESTORE-INSTRUCTIONS.md`, `RESTORE-TEST.txt`, потім `checksums/MANIFEST.sha256`
   (останнім) і перевірка `shasum -a 256 -c` вже на носії.
7. Зашифрувати, розкласти по місцях зберігання, від'єднати носії.

## Відновлення попереднього опублікованого матеріалу

**⚠️ Додано 15.09.2026 (Б4 Block B) — щойно шлях `publish-content.ts`
активовано (`docs/PANEL-hosting-and-approvals.md` §1.3), відновлення через
нього — рекомендований спосіб, не прямий `git checkout` на `main`.**
Причина: прямий `git checkout <sha> -- ... && git commit` в обхід guard'а
працює, але минає весь захист (allowlist, подвійний `content:guard`,
захист від застарілої публікації) — для контенту, яким керує панель, це
той самий ризик, що й для будь-якого іншого некерованого запису в `main`.

**Перевірений на синтетичному циклі (публікація A → публікація Б, що
видаляє фото A → відновлення A) спосіб:** відновлення — це **нова,
прямувальна вперед публікація**, а не повторна відправка старого
`content_sha`:

1. На гілці контенту зробити НОВИЙ коміт, чий `published.json`/
   `review-state.json` відтворюють версію A (текстові хеші можна взяти
   буквально ті самі, що були підтверджені для версії A — вони залежать
   лише від тексту, не від часу), і **додати назад байти будь-якого медіа,
   яке версія Б фізично видалила** (сам факт видалення файлу з диска не
   скасовується поверненням лише JSON-посилання — `content:guard`
   провалиться з «файл відсутній», якщо повернути тільки published.json).
2. Продиспетчерити `content-guard.yml` на SHA цього нового коміту.
   `publish-content.ts` прийме його, бо це **нащадок** останньої
   застосованої публікації (Б), а не її предок.
3. Випадкова спроба передиспетчерити СТАРИЙ SHA версії A напряму (замість
   нового коміту) — **гарантовано заблокована** (`REJECTED (6)`,
   «старіше за останню застосовану публікацію») — це і є захист від
   випадкового відкату, перевірений цим самим циклом.

Ручний шлях нижче (`git checkout <sha> -- ...`) лишається чинним, поки
Б4 не активовано, і як аварійний варіант, якщо сам guard недоступний.

`published.json` версіонований у Git, медіа **ніколи не видаляється**
автоматично (ні `content-guard`, ні панель — лише ручна дія в `/panel/video`
для відео). Тому відкат безпечний:

1. **Один матеріал** (напр. авто зникло / зіпсувалось у знімку):
   - у `/panel` натиснути **«Прибрати з сайту»** (unpublish) — робоча картка
     лишається, або
   - взяти попередню версію запису:
     `git show <старий-sha>:src/content/cms/published.json` → скопіювати
     потрібний елемент масиву назад і опублікувати через `/panel` (повторна
     публікація сама перезапише `review-state.json` для цього матеріалу).
2. **Весь знімок — три об'єкти з ОДНОГО SHA:**

   **Найпростіше (весь контент + усе медіа):**
   ```bash
   git checkout <старий-sha> -- src/content/cms/ public/images/cms/
   npm run content:guard        # має бути ✓
   npm run build                # знімок має збиратися
   git commit -m "restore content snapshot @ <sha>" && deploy
   ```
   Це відкочує **всі** матеріали до `<sha>` (не лише один). Для точкового
   відкату одного матеріалу — див. нижче.

   **Точковий відкат одного матеріалу — потрібні ВСІ три:**
   | Об'єкт | Шлях | Навіщо |
   |---|---|---|
   | знімок | `src/content/cms/published.json` | сам вміст картки |
   | підтвердження мов | `src/content/cms/review-state.json` | `content-guard` звіряє кожен мовний текст знімка з хешем тут; якщо матеріал згодом видалили, його хеші вичищені → відкат лише `published.json` **валить guard** (`текст не позначено перевіреним`) |
   | медіа знімка | `public/images/cms/<...>/<slug>/` (усі файли, на які посилається відновлений `published.json` — насамперед `_pub/<hash>.<ext>`) | **заморожені копії `_pub/<hash>` МОЖУТЬ бути видалені** кнопкою «Прибрати старі копії фото» або крок «Завершити видалення»; відкат без них → guard ✗ `файл відсутній у цільовому середовищі` |

   ```bash
   git checkout <sha> -- src/content/cms/published.json src/content/cms/review-state.json
   npm run content:guard        # покаже, яких медіафайлів бракує (за іменами)
   git checkout <sha> -- public/images/cms/gallery/<slug>/   # + інші теки з переліку помилок
   npm run content:guard        # тепер ✓
   ```

   **Звірено локально на ізольованому clone (задача 20:24 блок 5):** відкат
   знімка `57c2a07` (посилається на `_pub/8e9d45ba…png`, який видалено комітом
   `92c73d3`): лише `published.json` → guard ✗ (review-хеші + `файл відсутній`);
   `+ review-state.json` → guard ✗ (`файл відсутній`); `+ теку зображень` →
   **guard ✓**, `build` OK, 54/54 медіа, фото на диску = байт-точна копія A.
   Раніший запис «медіа гарантовано присутнє» **застарів** — після циклів
   заміни фото старі `_pub` копії прибираються.
3. **Робоча картка:** `git checkout <sha> -- src/content/cms/<kind>/<id>.json`
   (не впливає на опублікований знімок — guard лишається ✓; без неї матеріал
   у `/panel` — orphan-рядок «опубліковано, робочої копії немає»).

**Розмежування обʼєктів відкату:**

| Обʼєкт | Чим є | Спосіб відкату |
|---|---|---|
| Код + контент (`published.json`, робочі копії, `review-state.json`, медіа в `public/`) | версіоновано в Git | `git checkout <sha> -- <шлях>` — це **git-відкат коду**, а не бекап зовнішніх сховищ |
| Відео у Blob / БД заявок Postgres | **поза Git** | лише засобами провайдера (Blob-бекап, Neon PITR / `pg_dump`) — `git checkout` їх не відновлює |
| Секрети (env) | **поза Git** | лише з менеджера паролів власника (див. нижче) |

Матеріал, «опублікований, але без робочої копії» (відкат старого знімка, чию
робочу картку потім видалили), панель показує як orphan-рядок — це очікувано,
`/panel` це обробляє; за потреби відновити й робочу картку кроком 3.

4. Значення **ніколи** не потрапляють у Git, чат, звіти, скриншоти.
5. Відновлення: вручну повторно додати змінні у Vercel з цього запису →
   redeploy.

Агент може лише **нагадати** про цей крок і звірити список **назв** змінних —
