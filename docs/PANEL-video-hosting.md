# Відео авто: YouTube (зараз) і хостинг власних файлів (на майбутнє)

## Зафіксоване рішення власника: два способи

На сайті є **два незалежні способи** додати відео огляду до картки авто —
обидва існують у коді одночасно, жоден не видалений заради іншого:

- **А — YouTube (`external-link`, поточний основний спосіб).** Власник
  завантажує ролик на YouTube (Public або **Unlisted — це НЕ приватне**:
  переглянути й поширити відео може кожен, хто має посилання; воно не
  з'являється на вкладці «Відео» каналу і зазвичай не показується в пошуку
  YouTube — але якщо хтось додасть його до публічного плейлиста, воно
  стане доступним звідти; [офіційна довідка YouTube](https://support.google.com/youtube/answer/157177))
  і вставляє посилання в Keystatic. Сайт показує
  вбудований YouTube-плеєр (`iframe`). **Не потребує Vercel Blob і не додає
  плати за передачу відео через наш сайт** — файл і трафік обслуговує сам
  YouTube. Не варто стверджувати, що YouTube «назавжди гарантовано
  безкоштовний» — точніше: зараз це не вимагає окремої оплати з нашого
  боку. YouTube може показувати власний логотип, рекомендації після
  відео чи рекламу — це поведінка YouTube, не наша.
- **Б — власний відеофайл (`hosted-file`, додатковий спосіб на майбутнє).**
  Повна система завантаження MP4/WebM (`VideoUploader`, локальне сховище +
  адаптер Vercel Blob, гейт доступу, progress/cancel/retry, список,
  видалення) **повністю збережена в коді**, не видалена. Без підключеного
  Vercel Blob `/panel/video` показує безпечний стан «сховище не
  підключено» — форма завантаження файлу не монтується. Коли Blob
  підключать — функція запрацює без повторної розробки. Питання
  `public`/`private` для цього способу лишається відкритим і описане
  нижче (розділ «Рішення власника» щодо Blob) — воно **не блокує**
  поточну роботу сайту, бо Blob зараз не використовується взагалі.

Обидва способи проходять через те саме поле `video.mode` /
`video.src` (картка авто, Keystatic): `external-link` для YouTube (і будь-
якого іншого прямого https-посилання), `hosted-file` для завантаженого
через `/panel/video` файлу. Один спільний helper
(`src/lib/media/youtube.ts`) визначає, чи `external-link` є YouTube-
посиланням, і будує безпечну embed-адресу для сайту — детально в розділі
«Реалізація YouTube» нижче.

## Чому не через серверний маршрут

Vercel обмежує **тіло запиту Serverless/Edge Function до 4.5 МБ**
([docs](https://vercel.com/docs/functions/limitations#request-body-size)).
Відеоролики огляду — десятки-сотні МБ, тож вони **не можуть** проходити через
`/api/panel/video`. Тому:

| Режим | Як | Обмеження |
|---|---|---|
| Локальний (`next dev`, немає `BLOB_READ_WRITE_TOKEN`) | браузер `PUT`-ить байти на `/api/panel/video`; сервер робить magic-byte sniff і пише у `public/uploads/videos/` (git-ignored) | ліміту 4.5 МБ немає (це `next dev`, не Vercel); файли лише на цьому Mac |
| Хостинг (є `BLOB_READ_WRITE_TOKEN`) | **клієнтське завантаження Vercel Blob**: `upload()` з `@vercel/blob/client` обмінюється коротким токеном із `/api/panel/video` (`handleUpload`), далі браузер стрімить файл **напряму в Blob**, повз функцію | розмір ≤ 200 МБ (ліміт задає токен); тип лише `video/mp4` / `video/webm` |

## Що реалізовано

- `src/lib/media/videoStore.ts`:
  - `LocalVideoStore` — повний цикл (create → receive+sniff → list → head → remove), temp+rename.
  - `BlobVideoStore` — `list()` / `head()` / `remove()` через `@vercel/blob`
    (`list`/`head`/`del`), читає `BLOB_READ_WRITE_TOKEN` **на момент виклику**;
    без токена — `VideoStoreNotConfiguredError`, **ніколи** не пише в репозиторій.
  - `tokenRulesFor(pathname)` — правила видачі токена (префікс `panel/videos/`,
    лише mp4/webm, `maximumSizeInBytes = 200 МБ`, `addRandomSuffix`) — **юніт-тест**.
- `/api/panel/video` `POST` — дві гілки за `body.type`:
  - `blob.*` → `handleUpload({ onBeforeGenerateToken, onUploadCompleted })`;
    `onBeforeGenerateToken` **повторно перевіряє сесію** (`getStorage()`) і
    `tokenRulesFor(pathname)` перед видачею токена;
  - інакше → локальний «create upload target».
- `/panel/video` UI — `VideoUploader` гілкується за `mode`:
  - `blob` → `upload(pathname, file, { access:'public', handleUploadUrl,
    onUploadProgress, abortSignal })` — **прогрес, скасування (AbortController),
    повтор, помилки**;
  - `local` → XHR `PUT` з `xhr.upload.onprogress` + `xhr.abort()`.
- **Звʼязок із матеріалом**: після завантаження показується URL і покрокова
  інструкція вставити його в поле «Відео» авто в Keystatic (саме `video.src`
  публікується). Список завантажених відео позначає, яке авто кожне використовує;
  видалити файл, що **використовується**, з панелі не можна; осиротілі не
  видаляються автоматично.
- Гейт публікації: режим `hosted-file` без `src` або з небезпечним `src` →
  **блокер** (`carsGate`, `snapshot`, `content-guard`). Видалення/заміна відео в
  чернетці не чіпає опублікований знімок (у ньому власна копія `video.src`).

## Реалізація YouTube (`external-link`)

- `src/lib/media/youtube.ts` — єдиний спільний helper (жодних окремих копій
  логіки на сайті, в панелі чи в content-guard):
  - `looksLikeYoutubeUrl()` — м'яка евристика «це схоже на спробу вставити
    YouTube-посилання?»: hostname розбивається на доменні частини
    (лейбли), і домен вважається YouTube-подібним, лише якщо серед них є
    СУСІДНІ цілі частини `youtube`+`com`, `youtu`+`be` або
    `youtube-nocookie`+`com` — не підрядок, а точна пара лейблів. Це
    вирішує, чи взагалі застосовувати сувору перевірку нижче:
    `youtube.com.evil.example` розпізнається як спроба підробки (містить
    пару лейблів `youtube`+`com`) і передається суворій перевірці, яка
    його відхиляє; а `my-youtube-cdn.example` та
    `youtube-review-files.example` YouTube-подібними НЕ вважаються (слово
    «youtube» там — частина одного складеного лейбла, а не окрема
    частина домену) і лишаються звичайними зовнішніми https-посиланнями
    без змін.
  - `parseYoutubeUrl()` — сувора перевірка: лише `https`, лише точний
    реальний хост YouTube (`youtube.com`, `www.youtube.com`, `m.youtube.com`,
    `youtu.be`, `youtube-nocookie.com` — **точний збіг**, не підрядок, тож
    `youtube.com.evil.example` відхиляється), коректний 11-символьний
    video ID з усіх чотирьох підтримуваних форматів (`watch?v=`, `youtu.be/`,
    `/shorts/`, `/embed/`). Завжди **будує** нову безпечну адресу
    `https://www.youtube-nocookie.com/embed/<id>` — необроблений
    введений URL ніколи не потрапляє напряму в `iframe`.
- `src/lib/content/carVideo.ts` (`resolveCarVideo`) — на сервері, один раз,
  визначає `kind: "youtube" | "file"` і безпечний `src` для кожної картки
  авто; `src/lib/content/publishedCars.ts` викликає це для кожного
  опублікованого авто.
- `src/components/CarListingGallery.tsx` — лайтбокс рендерить `iframe`
  (`title`, `loading="lazy"`, `allowFullScreen`) для `kind:"youtube"`,
  чинний `<video>` — для `kind:"file"` (MP4/WebM/Blob/legacy без змін).
  Фокус-пастка діалогу тепер враховує й `iframe`.
- `src/lib/content/carsGate.ts` (`videoSrcProblem`, `getPublishBlockers`) —
  публікація з режимом `external-link`: коректний YouTube-URL публікується;
  URL, що ВИГЛЯДАЄ як спроба вставити YouTube (домен містить сусідню пару
  лейблів `youtube`+`com`, `youtu`+`be` або `youtube-nocookie`+`com`), але
  не проходить сувору перевірку (підроблений домен, зіпсований ID) —
  **блокує публікацію** з конкретною причиною (`video-link-invalid`), а не
  узагальненим «не підключено». Звичайний нерелевантний https-URL (прямий
  файл, Blob) і далі публікується без змін — поведінка не ламається.
  `scripts/content-guard.ts` використовує ту саму функцію — однакові
  правила в панелі й у CI.
- CSP (`next.config.ts`): і публічний сайт, і `/panel/video` (для
  живого прев'ю посилання перед копіюванням у Keystatic) дозволяють
  `frame-src` лише для `https://www.youtube-nocookie.com` — жодного іншого
  походження нікуди не додано.
- `/panel/video`: секція YouTube (`YoutubeLinkHelper`) видима **завжди**,
  незалежно від того, підключено Blob чи ні — валідація й прев'ю
  посилання не залежать від відеосховища.

## Стан

- **Код** — реалізовано.
- **Контракт** — перевірено через юніт-тести (`tokenRulesFor`, `blobPathnameFor`,
  `remove()` відхиляє не-URL, адаптер кидає NotConfigured без токена) і локальний
  прогін гілки `body.type` у маршруті.
- **Реальне сховище Blob — НЕ підключено.** Живу інтеграційну перевірку
  (справжнє завантаження ролика на Preview) можна зробити лише після видачі
  `BLOB_READ_WRITE_TOKEN`. Це **не** «жива перевірка Blob».

## Приватність чернеткових відео — компроміс, який ще не погоджено власником

**Важливо чесно розділити два різні факти:**

- У коді зараз **реалізовано лише `access: "public"`** — `VideoUploader.tsx`
  явно передає `access: 'public'` у клієнтський `upload()`. Це **рішення
  розробки**, зроблене щоб рухатись далі, а **не** підтверджене рішення
  власника.
- Публічний доступ для чернетки — це **компроміс, який власник ще має
  затвердити** (або відхилити на користь `private`) **ДО створення
  Blob-сховища**. Те, що код зараз пише `public`, саме по собі нічого не
  означає для Production — Blob ще не підключено (див. розділ «Стан» вище).

Наслідок поточної реалізації (`public`): **файл доступний за своїм URL одразу
після завантаження — ще до того, як картку авто опубліковано**. URL містить
довгий випадковий суфікс (`addRandomSuffix`), що робить його **практично
складним підібрати навмання** — це не криптографічна гарантія
«неможливо», а лише низька ймовірність випадкового вгадування. Але це **не
контроль доступу**: **хто б не отримав URL (будь-яким шляхом) — відкриє
відео**, жодної автентифікації Vercel тут немає. Сам факт завантаження файлу
**не** ставить його автоматично в пошукову видачу — пошукові системи не
сканують випадкові URL самі по собі. Але якщо посилання на файл **десь
з'явиться** (публічна сторінка, соцмережа, лог, індексований каталог тощо) —
відео стане знаходжуваним звідти. Документація Vercel **не дає гарантій щодо
індексації** публічних blob-URL; покладатися на «непередбачуваність суфікса»
як на постійний захист не можна.

### Факти про `private` Blob (офіційна документація Vercel, перевірено 2026-09-17)

- Приватне сховище створюється **окремо** від публічного — це властивість
  **СХОВИЩА**, а не окремого файлу, обирається при створенні, і **за
  документацією Vercel режим доступу не можна змінити після створення
  сховища.** Перейти з `public` на `private` (чи навпаки) можна лише
  створенням нового сховища й переносом файлів.
- Приватний блоб отримує URL вигляду
  `https://<store-id>.private.blob.vercel-storage.com/<pathname>` — він
  **не є публічним посиланням**: пряме звернення без автентифікації дає
  помилку. Прочитати вміст можна лише викликом `get()` **на своєму сервері**
  (Function), який сам перевіряє права і стрімить байти у відповідь, або
  через **підписаний (presigned) URL** (`issueSignedToken` +
  `presignUrl`).
- **Підписаний URL завжди тимчасовий: максимум 7 днів** (`validUntil`, за
  замовчуванням — 1 година). Постійного/безстрокового підписаного посилання
  не існує в принципі.
- **Це й робить `private` несумісним із поточною архітектурою `video.src` у
  теперішньому вигляді**: зараз у картку авто раз і назавжди записується
  ОДИН рядок-URL (`video.src`), який публічна сторінка підставляє напряму в
  `<video src>`. Для `public`-блоба цей рядок дійсний вічно. Для `private`
  такого постійного рядка отримати не можна — URL або взагалі не працює без
  токена, або протухає щонайбільше за 7 днів.
- Встановлений у репозиторії `@vercel/blob@2.8.0` **вже задовольняє** вимогу
  private-сховища (SDK ≥ 2.3) — апгрейд пакета для private не потрібен.
- Офіційна рекомендація Vercel: приватні сховища **не рекомендовані для
  файлів понад 100 МБ, якщо трафік не низький** — поточний ліміт відео в
  проєкті 200 МБ це перевищує, тож вартість/швидкість доставки при `private`
  вимагають окремої оцінки.
- Приватні блоби **не можуть бути проіндексовані** пошуковими системами — це
  підтверджено офіційною документацією (`private-storage`, розділ «SEO and
  search engine indexing»): будь-яке читання вимагає автентифікації, тож
  сканеру просто нема чим скористатись. Для `public` такої задокументованої
  гарантії **немає** — Vercel ніде не стверджує, що `addRandomSuffix`-URL «не
  індексується»; механізм тут інший і слабший: індексація малоймовірна лише
  тому, що пошуковик не має звідки дізнатись про сам URL, а не тому, що
  Vercel це якось блокує.

### Що саме довелося б доробити в коді для `private` (перелік, без реалізації)

1. Створити **нове** приватне Blob-сховище (не можна перемкнути наявне).
2. Замінити `access: 'public'` на `access: 'private'` у `VideoUploader.tsx`
   і у видачі токена в `route.ts`.
3. Додати серверний маршрут-проксі, що перевіряє автентифікацію публічного
   запиту й віддає відео через `get()` (Function), **або** підписувати
   `video.src` заново при кожному SSR-рендері сторінки картки (з
   перепідписом щонайбільше раз на 7 днів).
4. Змінити семантику поля `video.src` у контентній моделі: зберігати
   `pathname` у приватному сховищі замість постійного URL; сам
   доступний-для-браузера URL/токен генерувати «на льоту».
5. Оновити перевірки гейту публікації (`carsGate`, `content-guard`), які
   зараз, ймовірно, звіряють `video.src` як готовий URL, а не як pathname.
6. Врахувати вищу вартість доставки `private` (Blob Data Transfer + Fast
   Origin Transfer на запит Function → сховище, **плюс** Fast Data Transfer
   на відповідь Function → браузер) проти дешевшого прямого `public`
   Blob Data Transfer.

## Рішення власника

| Варіант | Що дає | Ціна питання |
|---|---|---|
| **А — `public`** (те, що зараз реалізовано в коді, але не підтверджено) | Найпростіше: працює з поточною архітектурою `video.src` без змін коду. Чернетка = «нелистований» URL (схоже на **Unlisted** на YouTube, а не на «Private» — Unlisted теж не приватне, будь-хто з посиланням відкриє відео) — практично складно підібрати навмання, захисту від індексації Vercel не гарантує, але хто отримає URL — відкриє. | Чернеткове відео технічно доступне за URL ще до публікації картки. |
| **Б — `private`** | Справжній контроль доступу до чернетки: без автентифікації файл узагалі не відкривається. | Вимагає доробок з переліку вище (нове сховище, проксі-маршрут або перепідпис URL щонайбільше на 7 днів, зміна семантики `video.src`, оновлення гейтів) — окремий етап розробки; дорожча доставка; ліміт 100 МБ-рекомендація Vercel при 200 МБ поточному ліміті відео. |

**Технічна рекомендація (не рішення):** відео авто — це промо-контент огляду,
який власник і так планує зробити публічним; чутливих персональних даних у
ньому немає. Для такого контенту варіант А («нелистований public URL») —
пропорційний компроміс, що не потребує додаткової розробки. Варіант Б
виправданий, лише якщо в майбутньому відео може містити щось, що не повинно
бути доступне нікому без сторонньої дії ще до публікації.

**Це рішення власника, не Клода.** Поки воно не зафіксоване явно — Blob-сховище
не створюється (див. «Що потрібно від власника» нижче), і код лишається на
поточній (не остаточній) реалізації `public`.

## Що потрібно від власника

Спочатку власник обирає варіант із розділу «Рішення власника» вище — **А**
чи **Б**. Ці інструкції умовні: до явного вибору жоден із двох підрозділів
нижче не виконується, і Blob-сховище не створюється.

### Якщо обрано А (`public`)

1. Vercel → проєкт `dream.car.vavd` → **Storage** → Create → **Blob** → access
   **Public** (готове відео на сайті публічне). Прив'язати до проєкту для
   середовищ **Preview** і **Production** (Development — за бажанням для
   локальних тестів).
2. Vercel сам додасть env `BLOB_READ_WRITE_TOKEN` у вибрані середовища.
   Вручну нічого вставляти не треба; **redeploy** гілки після цього.
3. Перевірка: `/panel/video` на Preview → завантажити тестовий ролик → має
   з'явитися в списку; вставити URL у поле «Відео» авто → чернетка показує відео.

### Якщо обрано Б (`private`)

1. Blob-сховище **поки не створювати** — public і private неможливо
   перемкнути одне на одне пізніше (див. «Факти про private Blob» вище), тож
   створення сховища «про запас» лише зафіксує неправильний вибір.
2. Спочатку окремою задачею реалізувати private-архітектуру з переліку
   доробок вище: нове приватне сховище, заміна `access:'public'` →
   `'private'`, серверний проксі-маршрут або перепідпис URL (максимум 7 днів
   на підпис), зміна семантики `video.src` (pathname замість постійного URL),
   оновлення гейтів публікації (`carsGate`, `content-guard`).
3. Лише після того, як ця реалізація готова й перевірена — створити
   **Private** Blob-сховище у Vercel і підключити його до Preview/Production.

саме включено, — таблиця тарифів вище.

**Оцінка навантаження:**

- Відео огляду авто: ~30–150 МБ кожне (стиснене 1080p, 1–3 хв). 1 ГБ Hobby ≈
  **7–30 роликів**. Кожен новий ролик — 1 розширена операція (запас великий).
- **Вузьке місце — Data Transfer.** Ролик 100 МБ, переглянутий 100 разів =
  10 ГБ = **увесь місячний ліміт Hobby**. Кілька популярних відео + звичайний
  трафік сайту легко перевищать 10 ГБ.

**Якщо перевищити Hobby-ліміт:** за офіційною документацією — доступ до Blob
**блокується**, оплата за перевищення **не стягується** («you will not pay for
any additional usage»), і потрібно зачекати, доки **не мине 30 днів** від
моменту перевищення (або перейти на Pro trial, що знімає ліміт одразу). Відео
на сайті тоді не віддаються, поки доступ заблокований.

**Висновок для рішення:** на Hobby Blob придатний для **невеликої кількості**
роликів із помірним трафіком. Перед публікацією багатьох/популярних відео —
рахувати очікувані перегляди × розмір проти 10 ГБ і, ймовірно, Vercel Pro
(окреме рішення про тариф) або зовнішній відеохостинг (YouTube unlisted /
Cloudflare Stream).

## Підсумок: що вже працює і що потребує сховища

| Питання | Відповідь |
|---|---|
| Що працює **без** додаткового сервісу | Локальний режим (`next dev`): завантаження, sniff, список, видалення, звʼязок із карткою — усе в `public/uploads/videos/` (git-ignored, лише на машині розробника). Публічний сайт віддає `video.src` зі знімка — якщо файл існує за URL. |
| Що потребує **Vercel Blob** | Будь-яке завантаження відео на hosted (Preview/Production) — через ліміт тіла функції 4.5 МБ. Потрібен `BLOB_READ_WRITE_TOKEN` (Vercel додає сам при створенні Blob-сховища). |
| Чи доступні **неопубліковані** файли за прямим URL | **Так.** `access:"public"` → файл віддається за URL одразу після завантаження, до публікації картки. URL має довгий випадковий суфікс (практично складно підібрати навмання, але не криптографічно «неможливо»; жодних гарантій щодо індексації Vercel не дає), але це **не** контроль доступу — хто отримає URL, той відкриє відео. Публічна доступність чернетки **не погоджена** — потрібне явне рішення власника (розділ «Приватність чернеткових відео»). |
| **Видалення** | З панелі не можна видалити відео, що використовується опублікованою карткою. Осиротілі файли **не** видаляються автоматично — лише вручну в `/panel/video`. Видалення в Blob незворотне. |
| **Резервування** | Blob **поза Git**. Бекап — окрема копія (cron-джоб у S3-сумісне сховище, приклад у docs Vercel) або ручний `vercel blob list/get`. Втрата файла ламає `video.src` у знімку (посилання, не копія байтів). |
| **Звʼязок із матеріалом** | Ручний: після завантаження власник копіює URL у поле «Відео» авто в Keystatic; публікується `video.src`. Список відео показує, яке авто кожне використовує. |
